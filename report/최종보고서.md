## 결과 요약

기능 시험은 T0·T1·T3·T4가 합격이고, T2 재실 인원은 빈 방은 정확하지만 사람이 많을 때 적게 세어 MAE 기준(≤ 1.0)에 못 미쳤다. 응용은 A1(재실 인원)과 A4(근접 경고)를 한 서비스로 묶어 12시간 재시작 없이 돌렸다.

- 보드: Jetson Orin Nano Super 8GB, MAXN\_SUPER, 호스트 venv (torch 2.14.1+cu132, ultralytics 8.4.184, TensorRT 10.16.2, OpenCV 5.0.0 FFmpeg 백엔드)

## 2. T0 연결·뷰어·지연

두 카메라 모두 끊김 없이 들어오고, "최신 1장 리더"를 쓰면 처리가 느려도 지연이 쌓이지 않는다. 웹캠은 화면까지 약 0.18초, IP 카메라는 약 0.5초 늦다.

| ID | 입력 | 결과 | 판정 |
| --- | --- | --- | --- |
| T0-1 수신 (30초) | 웹캠 720p·1080p | 30.0fps, 끊김 0, 최대 간격 45ms | 합격 |
| T0-1 수신 (30초) | IP 메인 2560x1440 / 서브 848x480 | 25.6 / 25.7fps, 끊김 0, 첫 프레임 1.0\~1.2초 | 합격 |
| T0-2 뷰어 | 웹캠 720p / IP 메인 | 보낸 FPS 29.9 / 25.0 | 합격 |
| T0-3 초점·각도 | IP 카메라 | 틸트를 낮춰 천장 비율 30% → 3%, 선명도 1,700 → 2,099 | 합격 |
| T0-4 지연 누적 (2분) | 웹캠 | (a) read() 그대로 742 → 860ms, (b) 최신 1장 7 → 36ms | 합격 |
| T0-4 지연 누적 (2분) | IP 카메라 | (a) 약 105초까지 계속 증가, (b) 1\~2초 안 유지 | 합격 |
| T0-5 재연결 | 웹캠 USB 뽑기 | 재연결 1회, 꽂은 뒤 최대 약 8초, 프로세스 유지 | 합격 |
| T0-5 재연결 | IP 랜선 뽑기 | 끊김 감지 30초 → 3초(읽기 타임아웃 설정 후), 전체 58 → 32초 | 합격 |
| T0-6 glass-to-glass | 웹캠 → Mac Chrome | 평균 약 180ms (165\~200, n=6) | 합격 |
| T0-6 glass-to-glass | IP → Mac Chrome | 평균 514ms (467\~550, n=6), 원본 송출은 680ms | 합격 |

- 웹캠은 드라이버 버퍼가 약 4장이라 read()를 그대로 쓰면 0.8초 뒤처진 채 고정된다. RTSP는 FFmpeg가 프레임을 버리지 않고 쌓아, 처리(약 3fps)가 카메라(25fps)보다 느리면 끝없이 밀린다.
- IP 카메라는 랜선이 빠져도 FFmpeg 기본 타임아웃 30초 동안 멈춰 있어, 열기 5초·읽기 3초 타임아웃을 넣고 실패 2번이면 다시 열도록 고쳤다.
- IP 카메라 원본(약 480KB/장)을 그대로 보내면 약 100Mbps라 브라우저가 깨졌다. 1280 폭 q70 릴레이(약 135KB/장)로 지연도 680 → 514ms로 줄었다.

## 3. T1 물체 인식

TensorRT FP16 엔진이 PyTorch보다 6.3배 빠르고(4.0ms) 정확도는 거의 같아, 이 보드의 기본 설정으로 썼다. COCO 밖 물체는 YOLOE-11l이 5종 중 4종을 맞혔다.

### T1-1·T1-7 엔진 속도와 정확도 (640x640, batch 1, coco128)

| 모델 | 추론 평균 / p95 (ms) | 전체 처리 (ms) | mAP50-95 | 전력 (W) |
| --- | --- | --- | --- | --- |
| PyTorch YOLO11n FP32 | 25.2 / 26.8 | 36.0 | 0.508 | 10.0 |
| TensorRT YOLO11n FP16 | 4.0 / 4.3 | 15.5 | 0.504 | 10.5 |
| TensorRT YOLO11n INT8 | 3.3 / 3.5 | 14.6 | 0.482 | 10.1 |
| TensorRT YOLO11s FP16 | 6.6 / 7.1 | 20.4 | 0.576 | 11.7 |

- INT8은 FP16보다 0.7ms 빠르지만 mAP가 4.5% 떨어져 FP16이 균형이 좋다. 전체 처리는 추론의 3\~4배로, CPU 전처리·NMS가 약 11ms를 쓴다.
- 1장당 에너지는 PyTorch 약 0.36J, FP16 엔진 약 0.16J.

### T1-4 조명 × 거리 (IP 카메라, 사람 conf 평균)

| 조명 | 2m | 5m | 8m |
| --- | --- | --- | --- |
| 밝음 | 0.929 | 0.894 | 0.887 |
| 어두움 | 0.921 | 0.868 | 0.851 |

- 6칸 모두 검출률 100%. 멀수록, 어두울수록 낮아지지만 8m에서도 0.85 이상이다. 어두우면 노출이 길어져 카메라 FPS가 25 → 약 17로 떨어지고, 움직이는 순간 conf가 0.44까지 내려갔다.

### T1-5·T1-6 추적·선 통과

- 사람 1명이 통로를 5번 왕복: IN 5 / OUT 5, 오차 0 (기준 ±1). 처리 약 24.7fps.
- 추적 ID는 마지막 왕복에서 한 번 바뀌었다(470 → 537, 기준 ≤ 1). 선을 넘어야만 세므로 개수는 영향을 받지 않았다.
- 이벤트는 MQTT(qos 1)로 발행해 구독 쪽 수신을 확인했다.

### T1-8 개방 어휘 (COCO 밖 5종)

| 방법 | 마이크 | 테이프 | 핸드크림 | 에어팟 | 쿠션 팩트 | 정답 |
| --- | --- | --- | --- | --- | --- | --- |
| YOLO11n 그대로 | remote | remote | remote | mouse | remote | 0/5 |
| 재라벨 (EmbeddingGemma 2) | remote | remote | 정답 | 정답 | remote | 2/5 |
| YOLOE-11s | 정답 | hand cream | 정답 | hand cream | earbuds case | 2/5 |

- 큰 모델(11l)은 11s가 "hand cream tube"로 몰던 물체를 구분했다. 대신 추론이 약 50 → 87ms로 느려졌다.
- 투명한 테이프 디스펜서는 모든 방법이 틀렸다. 재라벨은 후보에 "remote" 같은 흔한 COCO 문구가 있으면 그쪽으로 끌려갔다.
- T1-2·T1-3(COCO 기본 6종, 클래스 필터)은 별도 기록이 없다.

## 4. T2 재실 인원 카운터

빈 방과 1\~2명은 안정적으로 세지만, 강의실에 4\~7명이 있을 때는 가림 때문에 1\~2명 적게 세어 MAE 1.23\~1.77로 기준(≤ 1.0)에 못 미쳤다.

- 구성: IP 카메라 메인 스트림 → YOLO11n FP16 960, 2x2 타일(겹침 15%) → 구역 JSON(방 안 3구역) → 10초 중앙값. 약 10fps.
- 타일 경계에서 한 사람이 두 번 잡히는 문제는 "작은 박스의 60% 이상이 큰 박스 안이면 지우기"(포함 억제)로 줄였다.

### T2-8 정확도 (스냅샷에 사람이 직접 정답 입력)

| 평가 | 장면 | MAE | 편향 | ±1명 이내 | 빈 방 오판 |
| --- | --- | --- | --- | --- | --- |
| 1차 (40장) | 0명 9, 1\~3명 15, 4\~7명 16 | 1.23\~1.43 | +0.23\~+0.53 | 57\~60% | 0\~11% |

| 기준 |  | ≤ 1.0 |  | ≥ 80% | ≤ 10% |

- 범위는 통계 방식(스냅 raw, 10·30초 중앙값·p75)별 값. 30초 p75가 가장 좋았다(2차 MAE 1.40, ±1 47%).
- 1차는 4\~7명에서 많이(+1.62, 타일 중복), 2차는 포함 억제 후 적게(−1.66) 셈다. 뒷줄 착석자가 모니터·앞사람에 가려 반복해서 빠졌다.

## 5. T3 행동 패턴 인식

0.6초 다수결이 만세 깜빡임을 9번에서 0번으로 없애고(지연 0.31초), 행동 패턴 4종은 첫 시도 12번 중 10번을 맞혔다. 웹캠 C920 1280x720, YOLO11n-pose, 약 12\~15fps.

| ID | 시험 | 결과 | 판정 |
| --- | --- | --- | --- |
| T3-1 관절 | 정면 / 측면 / 뒷모습 | 보이는 관절 17 / 13 / 14개. 측면은 가려진 쪽 신뢰도 0.69 (카메라 쪽 0.97) | 합격 |
| T3-2 raw | 만세 10 / 한팔들기 10 | 깜빡임 9 / 0 (팔을 올리고 내리는 중간에 한팔들기로 잠깐 잡힘) | 문제 확인 |
| T3-3 안정화 | 만세 10 / 한팔들기 10 | 10/10, 깜빡임 0 / 10/10, 깜빡임 0. 지연 평균 0.31초 | 합격 |
| T3-4 손 흔들기 | 흔들기 10 / 한팔 들고 정지 10 | WAVE 10/10 / 오판 0/10 | 합격 |
| T3-5 악수 | 악수 5 / 나란히 서기 5 | 4/5 / 오검출 0/5, 오류 합계 1 | 합격 |
| T3-6 행동 패턴 | 4종 × 3회 | 첫 시도 10/12, 다시 하기 포함 12/12 | 합격 |

### T3-6 혼동 행렬 (첫 시도, 행 = 실제)

| 실제 \\ 판정 | 지나감 | 힐끗 봄 | 관심 있음 | 머무름 |
| --- | --- | --- | --- | --- |
| 지나가기 | 2 | 1 | 0 | 0 |
| 힐끗 | 1 | 2 | 0 | 0 |
| 관심 | 0 | 0 | 3 | 0 |
| 머무르기 | 0 | 0 | 0 | 3 |

- 틀린 2건은 모두 지나감↔힐끗 경계다. 고개를 돌리는 동안은 정면 점수가 0.6 미만이라 1초만 보면 지나감이 되고, 약 2초 보면 힐끗 봄이 됐다.
- 카메라를 통로와 직각(간판 방향)으로 돌린 뒤 시험했다. 통로를 길게 내려다보는 구도에서는 카메라 쪽으로 걸어오면 얼굴이 정면이 되어 지나가기가 관심 있음으로 나왔다.
- 한계: 시선이 아니라 얼굴 방향으로 판정해, 폰을 보며 카메라 쪽을 향한 사람도 관심 있음이 된다. 화면 밖으로 3초 이상 나가지 않으면 두 번의 시도가 한 추적으로 합쳐진다.
- T3-7·T3-8(직접 녹화와 GRU 학습)은 이전 실습에서 한 결과가 있다. 동작 GRU는 오프라인 점수는 높았지만 실시간에서 팔벌려뛰기·악수를 박수로 오판해 규칙 판정을 썼다.

## 6. T4 거리 측정 (웹캠 2대)

## 7. 심화 B1·B2

하드웨어 복원(NVDEC)은 같은 25fps를 CPU 복원의 1/4\~1/5 CPU로 내고, 웹캠을 RTSP로 송출해 보드에서 받아 검출하면 프레임 나이 약 50ms로 지연이 쌓이지 않았다.

### B1 하드웨어 복원 vs CPU 복원 (실시간 25fps, 60초)

| 입력 | NVDEC (GStreamer) | FFmpeg CPU | libde265 CPU |
| --- | --- | --- | --- |
| 1080p H.264 | 10.1% | 43.6% | - |
| 1080p H.265 | 10.4% | 53.0% | 126.8% |
| IP 카메라 H.265 2560x1440 | 15.2% | 56.0% | 122.8% |

- 수치는 프로세스 CPU(코어 1개 = 100%). 최대 속도는 NVDEC이 H.264·H.265 모두 약 165\~170fps로, 한계는 복원기가 아니라 BGRx 변환·메모리 복사 쪽이다.
- 사용 중인 OpenCV가 GStreamer 없이 빌드돼 추론 코드에서 바로 NVDEC을 쓸 수 없다. GStreamer appsink로 프레임을 받거나 GStreamer 포함 OpenCV가 필요하다.

### B2 웹캠 → RTSP 송출 → 보드 사람 검출

- 경로: 웹캠 MJPG → x264(zerolatency, 2Mbps) → RTMP → MediaMTX → RTSP → 최신 1장 리더 → YOLO11n → MJPEG 화면
- 받은 29.9fps, 처리 24.9fps, 추론 33.1ms, 프레임 나이 50.4ms, GPU 13.8%
- conf 0.4 → 0.3: 평균 사람 수 5.2 → 6.0명(약 15% 더 잡음), 대신 같은 사람에 박스가 겹치는 경우가 생김

## 8. 응용: A1 재실 인원 + A4 근접 경고 통합 서비스

A1과 A4를 한 프로세스로 묶어 12시간(10/30 16:55 \~ 10/31 04:55) 돌렸고, 재시작·카메라 재연결 없이 상태 점검이 4,320번 모두 정상이었다.

### 구성

- 프로세스 하나가 TensorRT 엔진과 CUDA 문맥을 공유한다(문맥마다 약 0.5GB라 메모리를 아끼려고).
- A1: IP 카메라 → YOLO11n FP16 960, 2x2 타일, 포함 억제 → 구역 → 10초 중앙값, 5fps
- A4: 웹캠 스테레오 → 정류 → YOLO11n FP16 640 + SGBM → 사람별 거리(무늬 게이트, 1초 중앙값) → near(< 1.0m) / mid / far(> 3.0m), 8fps
- 카메라마다 읽기 스레드와 자동 재연결. REST `/v1/occupancy`, `/v1/proximity`, `/v1/health`, MQTT 발행(인원은 retain 10초마다, 근접은 상태가 바뀔 때, 카메라 상태는 LWT)
- systemd 사용자 서비스(Restart=always), 시작 전 웹캠 자동 초점 끄기·60Hz 설정. 운영 모드에서는 이미지를 디스크에 저장하지 않는다.

### 카메라 뽑기 시험

- 16:35:50 웹캠을 뽑자 근접 상태가 "unknown (웹캠 없음/끊김)"으로 바뀌었고, 약 9초 뒤 다시 붙어 거리 측정을 이어갔다.
- 그동안 IP 카메라 재실 인원은 5fps를 그대로 유지했다. 한 카메라가 빠져도 나머지 파이프라인은 계속 돈다.
- 무늬·유효 비율이 부족한 순간에는 틀린 거리 대신 "측정 불가"를 내보냈다.
- 남은 확인: 보드 재부팅 후 3분 안 복귀는 기록이 없고, 에이전트 질의 연동(A5)은 하지 않았다. 두 서비스가 같은 GPU를 쓰므로 LLM을 함께 올리면 메모리가 부족할 수 있다.

## 9. 종합

카메라 입력·검출·동작·거리는 기준을 넘겨 실시간 서비스로 묶을 수 있었고, 남은 문제는 대부분 가림(재실 인원 과소 계수, 측면 관절)과 얼굴 방향 기반 판정에서 나온다.

잘 된 것

- 최신 1장 리더 + 재연결 + 타임아웃으로 지연이 쌓이지 않고 카메라가 빠져도 스스로 복구한다.
- TensorRT FP16(4.0ms)과 NVDEC(CPU 1/4\~1/5) 덕분에 두 기능을 한 보드에서 GPU 41%·전력 9.9W로 12시간 돌렸다.
- 동작·행동은 규칙에 시간 안정화를 더해 깜빡임 0, 행동 패턴 10/12.
- 스테레오는 재투영 0.144px의 보정과 무늬 게이트로 사람별 거리를 2.7m 이상에서 ±1.3%로 재다.

한계

- 재실 인원: 뒷줄 착석자가 모니터·앞사람에 가려 4\~7명에서 1\~2명 적게 셈다(MAE 1.4\~1.8).
- 개방 어휘: 작은 모델(YOLOE-11s)은 2/5, 투명한 물체는 모든 방법이 틀렸다.
- 행동 패턴: 시선이 아니라 얼굴 방향으로 판정해 지나감↔힐끗 경계가 흔들리고, 카메라 구도에 크게 좌우된다.
- 거리: 실측 오차가 이론 예측의 3\~10배이고, 흰 면·근접에서는 틀린 값을 확신 있게 낸다.
- 미완료: T1-2·T1-3 기록, T2-6 비교표, T2-9 30분 대조, 재부팅 복귀 시간, 에이전트 연동(A5).

개선 방향

1. 재실 인원: 카메라를 더 높이 달거나 두 번째 각도를 더하고, 머리·상반신 기준(앵커 center)과 30초 p75로 다시 평가한다.
2. 개방 어휘: YOLOE-11l을 쓰되 후보 문구에서 비슷한 COCO 문구를 빼고, 현장 참조 사진을 임베딩에 더한다.
3. 행동 패턴: 힐끗 기준을 정면 점수 0.5·누적 1초 근처로 다시 잡고, 짧게 끊긴 추적을 같은 사람으로 합친다.
4. 거리: 보드를 1\~4m에도 두고 다시 보정하고, 근거리 모드를 따로 둔다.
5. 운영: GStreamer 포함 OpenCV로 NVDEC을 추론에 연결하고, 재부팅 복귀 시험과 에이전트 연동을 마친다.
